# E3 desktop release and remote updates

The direct-distribution app already checks for updates every 30 minutes, downloads them automatically, and installs at launch when no meeting is active. The setting defaults to on. An E3 fork must use its own signed release feed: the ordinary stable build points at Anarlog's feed and trusts Anarlog's signing key.

For an E3 build, set these values in the release environment:

- `E3_UPDATER_ENDPOINT`: E3-controlled HTTPS feed URL with `{{target}}`, `{{arch}}`, and `{{current_version}}` placeholders. The service must return a Tauri-compatible signed update manifest and artifact for each supported platform.
- `E3_UPDATER_PUBLIC_KEY`: public half of E3's Tauri updater signing key pair.
- `TAURI_SIGNING_PRIVATE_KEY`: corresponding private key, held only in the release environment. Set `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` if the key is encrypted.
- `E3_APP_IDENTIFIER`: an E3-owned bundle identifier distinct from `com.hyprnote.*`.

Then build from the repository root with `node apps/desktop/scripts/build-e3.mjs` and optional Tauri build flags such as `--target`. The script applies the stable configuration, the macOS stable override when applicable, and finally an E3 override. It fails if any required value is missing or if the update feed/key/bundle identifier reuse the upstream values. Do not distribute a binary built through the ordinary stable command as an E3 release.

Before rollout, provision the feed and publish a signed test release through the E3 release pipeline. Verify an installed E3 build updates from that feed on each supported platform, that a meeting defers installation, and that the release is signed/notarized where required by the OS. The build script does not create the feed, signing key, release pipeline, or OS code-signing credentials.

The current E3 build keeps Anarlog's desktop deep-link schemes and Linux package replacement metadata. Treat it as the organization's Anarlog installation and remove an upstream Anarlog install before rollout. A side-by-side install needs separate deep-link, login callback, binary, and Linux package work; changing the bundle identifier alone does not provide that.

## Managed meeting capture

Deploy [`e3/managed_settings.json`](e3/managed_settings.json) beside each person's active `app.db` before the first app launch. The policy keeps launch at login, scheduled meeting auto-start, active Slack huddle auto-start, and automatic updates enabled. Anarlog applies launch-at-login on startup; the installer must start the app once after installation. Users must connect and enable their own primary E3 Google calendar, grant microphone and system-audio permissions, and choose a transcription provider. Slack huddle auto-start requires trusted Accessibility access and a matching active Slack microphone session.

For a scheduled Google Meet, the employee must also connect the same Google account through Anarlog's Google Meet integration. The calendar's tracking address, Google Calendar connection address, and Google Meet connection address must match exactly; only primary calendars under `e3group.ai` or `coreedgesolution.com` are eligible. Enable Google Meet API and People API in the E3 Google Cloud project. The Google Meet connection needs `meetings.space.readonly`, `userinfo.profile`, and `userinfo.email`; reconnect existing Meet accounts so they grant the added scopes. Deploy the API endpoint before distributing this desktop build.

The desktop polls for a due calendar event and asks the API whether that exact signed-in Google account is in the linked Meet's active conference. It starts capture only after a positive result and checks again immediately before listening. Provider errors, missing permissions, an ambiguous Meet account, or a mismatched calendar account prevent auto-start. A conference opened more than 15 minutes before the calendar start is ignored to avoid matching a reused meeting code. If overlapping events use the same Meet code, automatic start is skipped because the calendar occurrence cannot be identified reliably. Non-Meet scheduled links keep their existing auto-start behavior. Stopping remains governed by Anarlog's local microphone behavior; this change does not use Meet departure data.

Before rollout, test an E3-hosted Meet and an externally hosted Meet with the employee signed in, plus a wrong-account join and a no-show. Include a phone-only join: that is an accepted trigger, but the desktop still captures audio from the computer, so verify the resulting recording is useful in that setup. Google does not publish a freshness guarantee for participant records; measure how long the API takes to show a real join in the pilot.

## Shared calendar transcripts

Create an E3 shared workspace and provision each recorder as a member. Add its canonical lowercase UUID as `settings.shared_transcript_workspace_id` to the deployed `managed_settings.json`; the checked-in policy omits this value because a workspace ID has not been provisioned. A malformed ID prevents app database startup. Each user must sign in with an active Pro subscription. When the managed workspace ID is present, the desktop app automatically enables Cloud API & Connectors for that signed-in account. The managed policy does not grant Pro entitlement or workspace membership; provision both before rollout. In managed workspace mode, the Cloud API uploads only completed calendar-backed meetings with a finalized, nonempty transcript and shares those with E3. Existing Cloud API content uploaded before the managed policy is applied is not removed by this change.

With these prerequisites, the desktop client uploads its Cloud API snapshot and registers it as a candidate after a calendar-backed recording has a completed, nonempty transcript. In-progress captures and unscheduled Slack huddles are not published. Google calendar `iCalUID` and, for recurring events, `originalStartTime` identify the calendar occurrence across attendees; recordings without this identity stay private. Each occurrence has one stable shared meeting ID, even when a later candidate becomes the selected transcript. Only the selected snapshot is visible to workspace members. The client retries transient publication failures with its pending snapshot queue. Deploy the Google Meet attendance API and the shared candidate database migration before distributing this desktop build.

When the scheduled Meet presence check succeeds, Anarlog saves the connected account and active conference record with the local session. On a completed upload, the Cloud API asks Google for that account's Meet participant sessions, including re-joins, and measures how much of the recording overlaps verified presence. Configure the Sync service's trusted Core attendance origin before rollout. Missing permissions, expired Meet records, incomplete session pages, or open sessions leave the attendance score unknown. The server ranks eligible candidates by positive verified overlap, then transcript timing coverage and text length computed before cloud-size trimming. Selection is deterministic and recalculated as candidates arrive or become unavailable; it does not use Meet departure to stop capture. Pilot with two E3 accounts on one event, a recurring instance, a reused Meet link on a different event, a re-join, and a deleted or revoked selected owner. Confirm both attendees see one shared meeting and the same stable link.
